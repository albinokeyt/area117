# Revisión de Compras, precios y PostgreSQL — v1.5.0

## Problemas encontrados y correcciones

| Estaba ocurriendo | Corrección |
| --- | --- |
| Se intentaba interceptar `localStorage.setItem` sobre la instancia Storage; en un navegador esto no garantiza interceptar escrituras. | Intercepción de los métodos nativos del prototipo, detección de cambios reales y cola ordenada de peticiones. |
| Compras y consumidores elegían distintas copias por fecha/global. Las marcas podían recuperarse de una copia antigua tras el cierre. | Selector compartido del registro más reciente; una lista de marcas vacía es válida y autoritativa. |
| Las ventanas podían montar datos iniciales antes de terminar de descargar PostgreSQL. | Se cargan los datos del servidor antes de montar los editores; si falla la lectura, se muestra el error y se permite reintentar. |
| “Guardado” aparecía sin esperar la respuesta de la base de datos. | Compras, copia de precios y Postes esperan la confirmación. Las escrituras fallidas quedan pendientes, se avisa y se reintentan. |
| Una descarga podía restaurar datos viejos por comparaciones de relojes y volver a subirlos. | PostgreSQL es la fuente confirmada; se protegen las ediciones pendientes y se descartan respuestas de versiones anteriores. |
| El cierre borraba precios especiales, desactivaba ventas manuales y podía alterar precios actuales. | Solo copia `curr → prev` y `sale → prevSale`, conserva valores/ajustes manuales y limpia las marcas. |
| Postes aplazaba escrituras y podía conservar marcas o valores obsoletos al recibir datos externos. | Persistencia inmediata de cada edición, recarga completa al recibir el servidor y limpieza de marcas al cerrar, conservando valores. |
| Los colores de precios especiales dependían de ser un valor manual, aunque ya se hubiera cerrado el día. | La marca diaria depende del conjunto `modified`; el valor manual se conserva después de limpiarla. |
| Algunas fórmulas/PDF/EFI leían valores iniciales guardados de tarifas especiales en lugar de calcularlos desde Compras. | Se respetan las opciones manuales explícitas y el resto se calcula desde los precios actuales. |
| EFI buscaba campos inexistentes (`buy`, estructuras antiguas de Postes); las altas de estaciones escribían otro formato incompatible. | Se usan `curr` y `postes`, las altas usan el formato real de Compras y se pueden leer filas antiguas con `buyPrice`/`manualSalePrice`. |
| Gasolina usaba costes de GOA para variables de fórmula; algunos ceros se sustituían por precios iniciales. | Costes propios de Gasolina, cero como valor válido y variables para las columnas numéricas de GOA, Gasolina y AdBlue. |
| Las variables Bronco de Compras se sobrescribían con las del cuadro Bronco independiente de Postes. | Se mantienen espacios de nombres separados. |
| La Sábana emitía eventos que recargaban sus propios estados y volvían a disparar la publicación de cachés. | Solo notifica cambios efectivos a los consumidores; las fórmulas dependientes de Postes también se recalculan. |
| La cola del servidor solo protegía un proceso; dos contenedores podían sobrescribirse. | Transacción PostgreSQL con bloqueo de fila y combinación de tres versiones. Se conservan cambios independientes y las colisiones en una celda devuelven 409. |
| Borrar fórmulas/configuraciones en el navegador no enviaba la eliminación. | Se envían eliminaciones explícitas; una descarga no resucita claves eliminadas. |
| Un fallo de PostgreSQL se devolvía como estado vacío exitoso. | Error 503, sin inicializar precios encima de datos existentes. Inicialización de tablas protegida por bloqueo PostgreSQL. |
| El Excel de cierre reconstruía parte de las tarifas con reglas distintas a las ventanas. | Incluye valores publicados por Sábana, la tabla real de importación EFI y una hoja con toda la configuración persistida, incluyendo clientes y fórmulas. |
| El Dashboard mostraba precios, volúmenes y ganancias fijos de ejemplo. | Muestra medias y márgenes de los precios actuales y los cierres realmente registrados. Se retiraron las estimaciones inventadas. |
| El navegador arrancaba como administrador, recibía contraseñas y admitía una contraseña maestra alternativa. Las API no validaban sesión. | Inicio de sesión en el servidor, contraseñas con scrypt, sesiones en PostgreSQL con cookie HttpOnly, comprobación de permisos y respuestas sin contraseñas. Las contraseñas existentes se migran al iniciar sesión correctamente. |
| Usuarios podía mostrar éxito aunque fallara el guardado/borrado. | Se comprueba la respuesta del servidor, se propagan los errores y se protege al último administrador. |
| Los ejemplos de despliegue recomendaban SQLite y el build ignoraba errores de TypeScript. | PostgreSQL obligatorio, retirada del esquema Prisma/SQLite sin uso, ejemplos corregidos, build con validación de tipos y dependencias fijadas con `npm ci`. |
| Dependencias de producción antiguas con avisos de seguridad. | Next.js 15.5.28, SheetJS 0.20.3 desde su distribución oficial y actualizaciones de PostCSS/source-map/parser. |

Los modos antiguos “compra media/mínima” apuntaban a columnas que el editor no guarda y usaban descuentos de ejemplo. Se identifican como referencias al precio de compra actual para mantener compatibilidad; no se inventa un promedio de proveedores sin esos datos.

## Persistencia

El servidor utiliza exclusivamente PostgreSQL: `efi_server_state` (su columna JSONB existente), `efi_server_users` y la nueva `efi_sessions`. No se crean archivos JSON de datos ni se usa SQLite. JSONB es almacenamiento dentro de PostgreSQL. El navegador mantiene una copia de trabajo para la interfaz; los mensajes de éxito requieren confirmación de la base de datos.

Se conserva la estructura y el contenido de la base ya existente. No hace falta sustituir `DATABASE_URL` en Easypanel. Tras desplegar hay que recargar la aplicación e iniciar sesión: ya no hay acceso automático como administrador ni contraseñas maestras alternativas.

## Verificación

- `npm test`: 9 pruebas de selectores, fórmulas dinámicas, costes de Gasolina, cero, compatibilidad de filas antiguas, cierre, combinación de cambios, conflictos y contraseñas.
- `npm run test:e2e`: 5 pruebas con Chromium, compilación de producción y una instancia PostgreSQL aislada. Comprueban guardado real, cambio de pestaña, actualización de fórmula sin recargar, cierre, Excel, persistencia desde otro navegador, Postes sin marcas tras el cierre, transacciones concurrentes, acceso sin sesión, ocultación de contraseñas y errores de lectura/guardado.
- `npm run typecheck` y `npm run build`.
- `npm audit --omit=dev`: sin vulnerabilidades reportadas en las dependencias de producción.

Las pruebas se ejecutan contra una base temporal propia; no acceden a los datos de producción.

## Límites de esta revisión

No se ha accedido al panel de Easypanel ni se ha verificado su despliegue o su conexión de producción. La revisión y las pruebas no certifican individualmente todas las reglas comerciales de cada tarifa contra el libro Excel original.

`npm audit` completo mantiene cinco avisos de severidad alta en la cadena de herramientas de desarrollo de Tailwind 3 (`braces` y dependientes). No se ocultan. Quitarlos requiere sustituir esa cadena o migrar Tailwind; no se introdujo esa migración visual en esta corrección.

Referencias de las actualizaciones: [aviso oficial de Next.js](https://nextjs.org/blog/security-update-2025-12-11), [distribución oficial de SheetJS](https://docs.sheetjs.com/docs/getting-started/installation/nodejs/).
